## 3. Что означает ошибка и что проверить в кабинете

Официальный [справочник ошибок Alibaba](https://help.aliyun.com/en/model-studio/error-code) связывает `AccessDenied.Unpurchased` с отсутствием активации Model Studio. Это подтверждённая трактовка кода, но не просмотр состояния конкретного аккаунта: кабинет, договоры и платёжные данные не открывались.

**Permission: All и доступ сервиса — разные проверки.** По [документации API key](https://www.alibabacloud.com/help/en/model-studio/get-api-key), All снимает пользовательское ограничение ключа по моделям; [активация сервиса](https://www.alibabacloud.com/help/en/model-studio/activate-alibaba-cloud-model-studio) описана отдельно. С учётом успешного TTS нельзя утверждать, что весь аккаунт не активирован. Установлен лишь отказ конкретного Omni Realtime вызова; точная причина (доступ к модели/сервису, региональная доступность либо проблема провайдера) остаётся неподтверждённой. All на скриншоте не опровергает наблюдённый ответ и не доказывает необходимость покупки.

Порядок действий владельца:

1. Открыть Model Studio в регионе Singapore под владельцем добавленного workspace.
2. Проверить активацию сервиса. Если предлагается соглашение/проверка аккаунта — пройти её самостоятельно.
3. Проверить доступ workspace к `qwen3.5-omni-flash-realtime`; отдельно посмотреть состояние аккаунта/расчётов, если сервис уже активирован. Наличие задолженности не установлено; покупать ресурсы на основании одного кода ошибки не требуется.
4. Повторить сначала создание и обновление сессии. Критерий — именно `session.updated`.
5. Затем один короткий нейтральный ответ с непустыми аудио/текстом и успешным `response.done`, после этого — согласованная проверка микрофона.

Ключи, права, оплату и состояние сервиса эта работа не изменяет.

## 4. Как подключение устроено в BMF и что можно использовать

Изученный BMF-CYBERAGENTS использует готовый Realtime API через Node/WebSocket gateway. Браузер отправляет PCM16 mono 16 кГц; сервер проксирует `input_audio_buffer.append`. После окончания реплики отправляется commit, после подтверждения — `response.create`. На выходе PCM16 24 кГц и субтитры. Контекст хранится в одной сессии разговора. Полный сценарий не нужно заменять самописной голосовой моделью.

Режим кнопки задаётся `turn_detection:null`. В официальном API также описаны VAD-режимы, но **они не проверены новым ключом**. Для новой интеграции документация рекомендует `session.audio.input.format`, `session.audio.output.format` и `session.audio.output.voice`; прежние поля PCM/voice сохраняются для совместимости. [Client events](https://www.alibabacloud.com/help/en/model-studio/client-events).

Практическое ограничение прежнего адаптера, подтверждённое текущей проверкой: наш отказ пришёл как `{code, message, request_id}` **без `type`**. В BMF `server.mjs:353` рассматривается лишь `event.type === 'error'`. Поэтому такой ответ будет пропущен, а пользователь увидит общий обрыв соединения. При переносе нужно обрабатывать оба подтверждённых формата ошибок, не выводя реквизиты.

Статус: дефект **задокументирован, исходный BMF обработчик не исправлялся**. При будущем переносе сначала распознавать подтверждённый error-envelope даже без type, затем маршрутизировать типизированные события. До ready показывать безопасный код ошибки и завершать ожидание, не заменяя причину одним close1006. API-пробник уже фиксирует этот envelope; это не production-адаптер.

Дополнительные ограничения BMF по исходникам: нет таймаута ожидания ответа после ready; `response.done` не проверяет статус; нет восстановления контекста при reconnect и полноценного перебивания; проверка ограничения длины текста происходит после передачи аудио. Эти пункты — анализ кода, не воспроизведённые на новом аккаунте сбои.

Готовые компоненты для дальнейшей работы:

- Существующий BMF gateway на `ws`: подходящий протокольный пример, но перенос целиком без исправления обработки ошибок не рекомендован. В package.json BMF указан `ws ^8.21.3`; в текущем пробнике реально использован 8.22.0.
- [Официальный DashScope Python SDK](https://github.com/dashscope/dashscope-sdk-python), Apache-2.0. Доступен готовый Omni Realtime клиент. В текущем публичном README описана v1.27.0; это кандидат для Python-мастера, не установленная зависимость F. Перед интеграцией закрепить точную версию и проверить нужные методы.
- [Issue #6 SDK](https://github.com/dashscope/dashscope-sdk-python/issues/6) содержит реальный отчёт об обрыве streaming-ответа. Это не доказательство той же причины, что у нас, и не Omni-specific приёмка; он подтверждает необходимость обработки незавершённых потоков. Ключевое свидетельство именно нашего ограничения — сохранённый live-ответ API.

## 6. Предложение следующего малого шага

Standalone текст→аудио подтверждён. Следующий малый шаг при отдельном поручении — сверить возвращаемую схему turn_detection и подготовить серверный адаптер с секретами только на сервере, нормализацией ошибок, таймаутами и отменой.
